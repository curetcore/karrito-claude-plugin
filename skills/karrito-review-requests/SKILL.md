# Karrito review requests

Resolve exact store first. Use list_review_requests, optional step/orderId, limit1..100 (tooldefault20)/offset. It reads existing rows only: id/orderId/productId/step/sentAt/nextSendAt/expiresAt/createdAt/updatedAt/reviewId, omitting phones, collected message bodies and provider identifiers. Read total and paginate; counts on one page do not represent the full queue.

CREATED means recorded preparation, SENDING is an in-progress claim, and later pipeline steps are stored state. sentAt indicates a recorded send timestamp; it does not prove delivery, reading, customer consent or service health. COMPLETED is recorded pipeline completion, not independently verified WhatsApp delivery. EXPIRED does not identify provider/cap/data failure; do not invent a cause. OPTED_OUT must never prompt a retry, alternate channel or sending workaround. Missing sentAt is not universal proof of no message; this projection deliberately excludes provider IDs.

No sending, messaging retry, configuration toggle or customer-contact tool is added by this skill. Karrito manages these actions in /admin/reviews/solicitar under reviews:config and existing entry/exit/channel/payer limits. For cancellation, when your connection lists it, prepare_review_action uses operation cancel-request and legacy reviewId set to the exact request ID (the field means target ID for this operation). Inspect list_review_requests first; COMPLETED/EXPIRED/OPTED_OUT are terminal and cannot be canceled. Show the exact request to cancel and ask the merchant to confirm; only then execute the same stored action, handle and original idempotencyKey, within 5 minutes. The committed result is EXPIRED, no contact or sending. Same-key replay returns the original receipt despite now-terminal state; never retry with a fresh key after an uncertain response. A stale request requires fresh preparation and confirmation. If these descriptors are absent, route to existing admin and make the unavailable MCP action explicit. Configuration concretely means reviewDelayDays1/2/3/5/7 and reviewAutoEnabled in Karrito's review settings, not general administration; this workflow does not enable automation or alter scheduling. Route the human there to inspect settings and do not claim a link changed anything. Do not turn on automation, complete a pending order or change its test label as a shortcut for requesting a review.

Order completion can record review intent and an explicitly configured Karrito process may prepare sessions from real completed nondeleted orders, existing reviewAutoEnabled/delay/channel limits and stable idempotency. Intent/prepared/processed are not sent/delivered. Never manufacture a receipt or invoke a provider from a draft. Customer phone and contact permissions cannot be inferred from reading an order or request.

Examples: “Which requests are queued?” → read CREATED/SENDING as states, paginate and distinguish evidence; “Did everyone receive it?” → report only stored evidence and unknown delivery; “Cancel requestX” → exactstore/id/nonterminal state, prepare cancel-request, merchant confirmation, execute original action/key; “Send to all buyers” → explain scope/channel/payer controls in admin, no tool execution; “Retry opted-out customers” → preserve opt-out and do not retry.
