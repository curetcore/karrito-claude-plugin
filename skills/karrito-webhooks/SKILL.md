# Karrito webhooks and existing automation
Select the exact store. `list_store_webhooks` returns bounded saved metadata (limit1–100, default20; offset default0), recognized configured events, active flags and an opaque destinationReference. The reference is not a destination URL. `list_store_webhook_logs` needs the own webhook ID, returns bounded recorded HTTP outcomes and UNVERIFIED processing, never payloads, response bodies or URLs. `success` does not prove recipient processing; an absent/expired log is not evidence of failure or success. Unknown stored event names are redacted and counted; unknown log event is null.
Supported subscriptions are `order.created`, `product.created`, `product.updated`, `product.deleted`. No `order.updated`, new scheduler or automation engine is available here. Existing product-delivery adapters are at least once; receiving systems need deduplication. This inspection does not send or retry anything. Native deletion cascades historical logs; private safeguards are narrower and do not repair that native policy.

## Webhook change workflow
`prepare_webhook_action` / `execute_webhook_action` are available only when your connection lists them. Prepare an exact own target and `update` body with only `events` and/or `isActive`, or `delete`. Events must be recognized and unique; empty/extra/URL/secret bodies are rejected. URL changes stay native UI. Preview must contain only redacted target metadata and exact intended events/active state. Human approval is via authenticated confirmation, outside MCP; never autoapprove. Use the returned handle with one stable idempotencyKey after approval. A retry replays the original receipt after fresh authorization; changed target or permission requires a new review.
Any pending product-operation recipient snapshot blocks private update/delete, including successful recipients in a partially completed operation. Explain the denial; do not delete logs, clone snapshots, clear pending flags or force retries. Cache PENDING is saved intent, not refreshed UI or provider delivery. Existing native update is Pro and settings:edit; native deletion preserves its exit policy without Pro. Private integration still requires existing store:write, settings:edit and current authenticated MCP API entitlement, so do not infer private access from the native exit path.
Create, secret rotation, destination URL editing, OAuth and test sending remain native workflows. Do not expose bearer URLs/tokens or call a receiver automatically. Report prepared/approved/executed separately from actual delivery.
