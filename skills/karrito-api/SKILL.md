# Integrate using real Karrito API
Use when someone is building an integration for their own Karrito store. Treat current available tool schemas and the declared API v1 contract as the source; do not fabricate endpoints, output fields, OAuth scope names or provider promises. Inspect the user's installed/versioned contract before writing runnable code. Distinguish legacy API-key integration, delegated MCP reads and delegated write workflows, which are available only when your connection lists them.
Get the store choice explicitly. Account `stores:read` only lists accessible stores; it is not store-data or write consent. Store reads use existing `read`; writes need existing resource-specific scopes plus fresh membership, business permission and API entitlement. Do not issue keys, expand scopes or use a global platform credential. Guide key/OAuth setup through the native screen; never request pasting secrets into chat.
Example readonly paths covered by available tools: GET `/api/v1/store/connections`, GET `/api/v1/store/webhooks`, GET `/api/v1/store/webhooks/{id}/logs`, GET `/api/v1/store/team`, GET `/api/v1/store/onboarding` and GET `/api/v1/stats/report`. Match exact required IDs, bounded pagination and structured outputs; do not turn opaque destinationReference into a URL. Ranged metrics use [from,to), ORDER_CREATED_AT and per-order currency; no inferred attribution. Reject/handle denied or malformed responses, not fabricate zeros.
Mutation reliability: the optional routine tools, when your connection lists them, classify only D1–D5 and use exact payload/version/stable-key delegated receipts without panel approval; inspect edits first and follow karrito-products for the full bounds. They remain OFF by default and require actual discovery. Sensitive prepare/execute handles bind an exact intent: prepare returns a private handle already authorized for the connected merchant, valid 5 minutes. Never automatically switch workflow after a routine denial or uncertain result. There is no approval tool or page; keep one stable idempotencyKey, distinguish committed receipt/replay from an unverified timeout, and recheck stale data before proposing a new intent. No private webhook URL changes, tests, creation, secrets or ownership transfers. A guide or a test result is not proof that OAuth or a tool works for a given merchant.
For existing webhooks describe only recognized events and current native signature/deduplication documentation when available; do not send test traffic, add a new automation engine or assert exactly-once delivery. Give the smallest integration example consistent with the real installed schema and explicitly state unexecuted steps. No provider activation or marketplace listing is implied by these guides.
